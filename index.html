Voice calls over QUIC, on a server you own.

VoQuic, also called Pulse Relay, is a self-hosted calling server. Clients sign in over WebSocket, ring each other, then send Opus audio as QUIC datagrams through the relay. It ships with a browser UI and starts with one command.

Voice is a cost line, a privacy risk and a latency problem.

Most teams rent calling from a platform and inherit its pricing, its data path and its network behavior. VoQuic puts all three in your hands.

Cost follows hardware

Hosted voice is billed per seat or per minute. VoQuic runs on a machine you already have, so the bill tracks the server, not the headcount.

Calls stay on your network

Presence, signaling and audio all flow through your own relay. There is no third-party media path to review when a customer or auditor asks where voice goes.

Voice is only useful now. QUIC datagrams skip retransmission, and a jitter buffer with loss concealment smooths over what goes missing.

    Every feature in the repository, and why it matters.

    Each item below comes from the VoQuic source: the server launcher, the native client, and the requirements file. The line in bold is the business reason it exists.

    Signaling and call control

    A WebSocket channel carries everything that is not audio: who is online, who is calling, and what state each call is in.

    WebSocket signaling endpoint

    Clients connect to /ws and can pass ?client_id= to keep a stable name.

    Name devices after places, like DOCK-3 or FRONT-DESK, and calls read like your org chart.

    Registration

    The server confirms the client ID and tells the client which QUIC port to use for audio.

    No manual port setup on any device.

    Presence list

    CLIENT_LIST returns everyone online along with their current status.

    Callers see who is free before they dial.

    Ring, accept, reject

    CALL reaches the target as CALL_INCOMING with the caller and a call ID. The target replies CALL_ACCEPT or CALL_REJECT with a reason.

    A declined call is a clear outcome, not a timeout.

    End with a reason

    CALL_END carries a reason string, and both clients return to IDLE.

    Support teams get something concrete to log.

    Mute sync

    Muting sends MUTE with the call ID and a muted flag. The peer is notified and the muted client stops sending audio.

    Both people know why it went quiet.

    Explicit call states

    IDLE, RINGING, QUIC_CONNECTING and VOICE_ACTIVE describe every client at all times.

    Easy to build status lights, dashboards and tests around.

    The media path

    Once both sides agree, audio leaves the WebSocket and moves to a purpose-built voice channel.

    Signaling-to-media handoff

    QUIC_INFO delivers the call ID and media port. The client answers with CALL_CONNECTED.

    Audio starts only after the client confirms it is ready.

    Datagram media transport

    Voice frames go to the server's QUIC port (4433 by default) as individual datagrams, with no retransmission queue.

    Stale audio is never replayed late, so the call stays live.

    Voice packet format

    Each packet holds a call ID, sender ID, sequence number and the audio payload. VoicePacket.parse() reads it back.

    Sequence numbers let receivers reorder frames and spot gaps.

    Opus codec

    Audio is encoded and decoded with Opus in fixed-size frames.

    Opus is designed for speech: clear voice at modest bandwidth.

    20 ms transmit loop

    While a call is VOICE_ACTIVE and unmuted, the client sends one frame every 20 ms.

    That is 50 packets a second per direction, which makes capacity planning simple arithmetic.

    Resilience

    Real networks reorder, delay and drop packets. These pieces keep speech intelligible when they do.

    Jitter buffer

    Incoming packets are pushed in as they arrive and popped in order at playout time.

    Smooths the uneven arrival Wi-Fi and mobile links produce.

    Packet-loss concealment

    When a frame is missing, pop() flags it and decode(None) synthesizes a stand-in.

    A lost packet becomes a brief blur instead of a dropout.

    Concurrent async loops

    Signaling, media receive and media transmit run as separate asyncio tasks.

    Control traffic and audio run independently of each other.

    Run and deploy

    Small enough to understand, flexible enough to move from a laptop to a server room.

    One-command start

    python run.py serves the web UI and signaling on port 8000.

    From clone to first call in minutes.

    HTTPS mode

    python run.py --ssl, or USE_SSL=1, serves on 8443 with a self-signed certificate that is generated for you.

    Browsers require HTTPS before other devices can use the microphone.

    Environment configuration

    HOST, HTTP_PORT, HTTPS_PORT and USE_SSL change the bindings without touching code.

    Fits containers, services and CI.

    LAN-ready by default

    The server binds to 0.0.0.0 and prints a LAN URL pattern, so any device on the network can join.

    Works on a closed site network with no internet.

    Lean stack

    FastAPI, Uvicorn, Pydantic and Starlette. Four dependencies in total.

    A small surface to audit, patch and host.

    Clients and quality

    Two ways to place a call, plus tests to keep changes honest.

    Browser client

    The server serves the web UI on the same port as signaling.

    Nothing to install for end users.

    Native CLI client

    client.py takes commands: C <id> call, A accept, R reject, M mute, E end, Q quit.

    Scriptable testing, and a reference for building other clients.

    Test suite

    A tests/ directory ships with the repository.

    Regression safety as you extend the system.

    Datagram to the relay

    Sent to the server's media port, 4433 by default
    Unreliable delivery: no retransmit

    Voice packet header

    Read back with VoicePacket.parse()
    call_idsender_idsequence

    Opus payload

    One 20 ms frame of encoded speech

    • The audio itself

      Opus compresses 20 ms of speech into a small payload. Created by codec.encode(), restored by codec.decode().

    • Who, which call, which frame

      Built by create_voice_packet(call_id, sender_id, sequence, payload). The sequence number is what lets the jitter buffer put frames back in order.

    • How it travels

      pkt.serialize() turns the packet into bytes, which are sent to the relay as one datagram. If it is lost, nothing waits for it.

    What QUIC's design offers live voice.

    The protocol properties that matter for calling, compared between audio over a WebSocket on TCP and audio as QUIC datagrams, which is the model VoQuic is built around.

    Audio over WebSocket (TCP)Audio as QUIC datagrams (VoQuic's design)
    When a packet is lostLater data waits until the lost segment is retransmitted, so the whole stream stalls.Datagrams are unreliable by design. The receiver conceals the gap and keeps going.
    Connection setupA TCP handshake, then a TLS handshake, then the WebSocket upgrade.QUIC combines transport and TLS 1.3 setup into one handshake.
    Changing networksThe connection is tied to an address pair, so moving from Wi-Fi to mobile usually drops it.QUIC connections use connection IDs, which are designed to survive address changes.
    EncryptionOptional layer on top of the transport.TLS 1.3 is built into the protocol.

    A note on the current code: the native client sends its voice frames through a plain UDP socket to the relay port, and requirements.txt does not include a QUIC library. Properties such as TLS 1.3 encryption and connection migration come from a full QUIC stack, so treat them as what the design can deliver once one is in place.

    Make your first call in two minutes.

    You need Python and a network. Start the server, then open the web UI on two devices, or use the CLI client in two terminals.

    Install and start the server
    git clone https://github.com/sripad2020/VoQuic
cd VoQuic
pip install -r requirements.txt
python run.py            # http://localhost:8000
python run.py --ssl      # https://localhost:8443
    Call from two terminals with the native client
    pip install websockets
python client.py 192.168.1.20 CLIENT-A
python client.py 192.168.1.20 CLIENT-B
# in CLIENT-A:
C CLIENT-B
# in CLIENT-B:
A
    SettingWhat it does
    HOSTBind address. Default 0.0.0.0
    HTTP_PORTWeb UI and signaling. Default 8000
    HTTPS_PORTSame, with TLS. Default 8443
    USE_SSLSet to 1 for HTTPS, same as --ssl

    On a phone, a self-signed certificate shows a warning. Tap Advanced, then continue to the site.

    Built to grow into production.

    VoQuic is a compact foundation. These are suggested next steps for a business rollout, not features in the repository today.

    Proposed roadmap, not shipped functionality

    Live microphone and speaker in the CLI client

    The client currently sends placeholder audio frames. Wiring in real capture and playback turns it into a full reference client.

    A full QUIC transport

    Adopting a QUIC library on both the relay and the clients would bring TLS 1.3 encryption and connection migration to the media path.

    Authentication and per-call encryption

    Token-based sign-in and end-to-end keys would satisfy healthcare, finance and enterprise security reviews.

    Group calls and conference rooms

    Mixing or forwarding several senders in one call opens team channels, dispatch groups and all-hands.

    Metrics and call records

    Loss, jitter and duration per call give operations teams a dashboard and give support a paper trail.

    Containers and high availability

    A container image and a second relay node move the service from a single box to a resilient deployment.

    Web and mobile SDKs

    Packaging the signaling and media client as a library lets other teams add calling to their own apps in days rather than weeks.

    Routing and queues

    Ring groups, hold queues and call transfer make it fit contact-centre and front-desk workflows.
